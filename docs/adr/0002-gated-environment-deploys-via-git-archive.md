# The gated environment's code only changes via `invoke deploy`, sourced from a curated git-archive snapshot

`scripts/`, the dashboard code under `observability/`, and the `backup` service's build inputs are bind-mounted live or built from the working tree today, so any restart of the hot environment — including via plain `invoke up` or `invoke setenv` — picks up whatever's currently on disk, uncommitted work-in-progress included. A new `invoke deploy [ref]` command (default `origin/main`, fetched first) closes that gap: it extracts exactly `scripts/`, `observability/dashboard/`, `observability/combined_dashboard.py`, `requirements.txt`, and `infra/Dockerfile.backup` from the target ref via `git archive | tar -x`, wiping and recreating `.deploy/deployed-code/` from scratch each time and recording the deployed commit in `.deploy/DEPLOYED_SHA`. Only the [gated environment](../../CONTEXT.md) (named by `DEPLOY_GATED_ENV`, currently `all_playlists`) is affected: its `workflow`/`dashboard` containers bind-mount code from `.deploy/deployed-code/` instead of the working tree (repointed via a `CODE_ROOT` compose variable), and the singleton `backup` service — which isn't scoped to any one environment — always builds from that same snapshot regardless of which environment is hot. Every other environment keeps mounting the live working tree and rebuilding instantly on `invoke up`, unchanged.

**Considered options:**
- *Isolation mechanism*: `git worktree add` was rejected — a worktree is a full, independently runnable checkout including `docker-compose.yml`, `tasks.py`, and every Dockerfile, so a stray `docker-compose up` run from inside it would stand up a second live stack (second slskd session on the same Soulseek credentials, duplicate Spotify/SoundCloud scraping). A `git checkout <ref>` in place was rejected too — it would require a clean working tree on every deploy, blocking continued edits while the gated environment sits behind. The git-archive extraction gets the same cheap, no-rebuild-needed update as a worktree without leaving anything behind capable of running Compose on its own.
- *Scope*: Only `scripts/`, the dashboard code under `observability/`, and `backup`'s build inputs are gated — infra/Dockerfile/`.env` changes for `workflow`/`dashboard` still take effect immediately via ordinary `invoke up --build`. This targets the actual failure mode (live-mounted Python code) rather than gating everything that could possibly affect the gated environment.
- *Topology*: Same machine throughout — no separate deploy target host exists or is planned. "Deployed" means "sourced from a blessed git ref," not "shipped to different hardware."
- *Restart safety*: `invoke deploy` does a plain restart of the affected containers rather than draining in-flight downloads or a backup pause first, leaning on the existing SIGTERM handling and backup self-heal logic (fixed in `82498fb`) that already tolerate abrupt restarts.
- *Backup service scope*: Included in the gate even though the original motivation was `workflow`/`dashboard` specifically, because `backup` is a single always-on service touching every environment's real data, not scoped to `DEPLOY_GATED_ENV` — leaving it ungated would exempt the one component with the largest blast radius.

**Consequences:**
- `backup`'s `requirements.txt` is pinned to the deployed snapshot, so a new dependency added for `backup_manager.py` won't reach the container until the next deploy, even though `workflow`/`dashboard` pick up `requirements.txt` changes immediately on `invoke up --build`. Accepted as a minor, arguably desirable side effect given backup's blast radius.
- No live/dev path exists for testing `backup_manager.py` changes inside the actual container — validation happens via `tests/test_backup_manager.py` (already exercises the logic against a real temp SQLite DB) plus review before merging to `main`, not by running the dockerized service against work-in-progress code.
- `invoke up`, `invoke build`, and `invoke setenv` now refuse to start the gated environment if `.deploy/deployed-code/` doesn't exist yet, rather than silently building from the working tree — the first deploy is a required, explicit step with no auto-bootstrap.
- `observability/logs/` stays mounted from the working tree unconditionally, in every environment — only the dashboard *code* under `observability/` is sourced from the deployed snapshot, so logs never split across two locations depending on which environment is hot.
