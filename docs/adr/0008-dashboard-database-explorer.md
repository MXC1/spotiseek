# The dashboard gets a read-only Database explorer over the live database, not a SQL console

The dashboard's tabs are curated summaries, so debugging one stuck or failed track, or checking that the data still agrees with itself after pruning and folder rebuilds, means reading raw rows the dashboard never shows. A new **Database** tab fills that gap with two sub-views — **Tables** (a browser) and **Audit** (canned checks) — for the [hot environment](../../CONTEXT.md) only. It is strictly read-only, reads through the live `TrackDB` connection under hard guardrails, and looks slightly beyond the database (file existence) only when asked.

## Decision

1. **Purpose and scope.** Debugging stuck/failed tracks, auditing integrity, and casual browsing. No editing or repair, no raw-SQL box, no CSV export. Hot environment only — no cross-environment picker.
2. **Tables view.** Every table is auto-discovered from `sqlite_master` (currently the five domain tables plus the scheduler's `task_runs`/`task_state`; a future table appears with no code change). Table and column identifiers are validated against `sqlite_master` / `PRAGMA table_info`, never string-built from request input; values are always bound parameters. Each table pages (default 25; 10/25/50/100; hard cap 100), sorts server-side, and filters per column. Page, sort and filter state lives in request params, as on the Blacklist tab. Data refreshes manually — no polling. Declared foreign keys become click-through links (today only `playlist_tracks` declares any: to `tracks` and `playlists`).
3. **Track detail.** Clicking a track opens its own URL-addressable view, `/database/track?track_id=…` (a query param, because SoundCloud track IDs contain `/`). It shows the full row; its playlists and their folder memberships; any matching blacklist entry (username + normalized file name); its status age (see ADR 0009); and, computed on demand, whether its file exists with size and mtime, and per playlist whether its m3u8 line is the resolved path or still the placeholder comment.
4. **Audit view.** Three DB check groups — referential integrity (playlist_tracks pointing at a missing track/playlist, tracks in no playlist, folder memberships for unknown playlists, playlists with no membership), status/field consistency (e.g. `completed` with no file path, `downloading` with no download UUID, `failed` with no reason), and stuck tracks by status age — run on page load and show a count each. A stray `local_file_path` is flagged only on `blacklisted` tracks, not on every non-completed one: a quality upgrade legitimately keeps the old file's path while the track is `redownload_pending`/`searching`/`downloading` again, so flagging those would drown the real findings. **Disk checks** (a completed track's file missing, a playlist's m3u8 missing, files in `imported/` no track references) run only when clicked, uncached. The orphan-file scan covers `imported/` only — the one media directory the dashboard mounts — and audio extensions only. A **Database health** section, also on click, shows file size, page and freelist counts, `journal_mode`/`synchronous`, whether a leftover `-journal` file exists, and the result of `PRAGMA quick_check`.
5. **Read path: the live shared `TrackDB` connection, under guardrails.** Every read is one bounded `fetchall()` with no cursor left open. The explorer never calls `commit`/`rollback` and never changes pragmas or `row_factory` on the connection, which is shared across request threads and the dashboard's own blacklist/import writes. Anything expensive (disk checks, `quick_check`) is click-only. SQL lives in new `TrackDB` read methods (ADR 0003); filesystem checks live in the dashboard route module, which reads the `(id, path)` rows first and only then stats files, so the DB is never held during slow I/O.

## Considered options

- **A raw read-only SQL box.** Rejected. It needs a hard read-only guarantee, and `PRAGMA query_only` is connection-wide, so it would race the dashboard's own writes on the shared connection; the alternative, a second connection, is exactly the ad hoc access CLAUDE.md forbids. Per-table browsing plus canned checks cover the stated jobs.
- **Editing or repairing rows.** Rejected: a write surface on a database that has been corrupted before. One-off repair still goes through a real task, per CLAUDE.md.
- **Cold-environment access.** Rejected: opening another environment's DB through `TrackDB` runs its `CREATE`/`ALTER` migrations, i.e. writes to a database meant only to be read.
- **A periodic read-only snapshot for the explorer to read.** Rejected. It removes lock contention entirely, but the data would be minutes stale — defeating "why is this track stuck right now?" — and it needs a new scheduled task, extra disk, and a Refresh that triggers a task instead of re-querying.
- **HTMX polling refresh.** Rejected: extra reads under the rollback journal, and it re-renders a table mid-inspection. (No dashboard template polls today either.)
- **A live slskd lookup in the track detail view; duplicate-file and blacklist-conflict checks.** Rejected as scope: a network dependency in a database tab that overlaps Execution Inspection's log streaming, and checks the stated jobs don't need.
- **Layout alternatives.** Two top-level tabs, one long scrolling page, a side-panel or inline-expanding detail view were rejected in favour of one tab with sub-views and an addressable detail page.

## Consequences

- **Concurrent access is safe from corruption, but not free.** The dashboard and workflow already share this DB file from separate containers under the rollback journal (`journal_mode=DELETE`, chosen because WAL's shared-memory file is unreliable over this mount). On 2026-09-21, a throwaway probe database (never a live DB) exercised exactly that pairing across the workflow and dashboard containers, on the real mount (`9p`/`drvfs` `E:\`, WSL2 kernel 6.18, SQLite 3.46.1, Python 3.11):
  - While one container held an `EXCLUSIVE` lock, the other's read *and* write were both refused with `database is locked` after the 1 s timeout, and once released it read a consistent result (holder's row present, contender's absent).
  - While one container held an open read cursor, the other's `commit` was refused after 1 s and succeeded 0.01 s after the cursor closed. **A leaked read cursor stalls workflow writes** — this is why guardrail 5 exists.
  - 200 concurrent inserts from each container plus a concurrent reader lost nothing (400 of 400 distinct rows), surfaced no lock errors, and left `integrity_check` `ok`; the reader saw no errors and no decreasing counts.

  Locks are honoured across containers, so the real risk from the explorer is contention (workflow writes blocked up to the 30 s timeout, then `database is locked`), not corruption. **Caveat:** this was one small run (400 rows, ~5 s); it does not cover long-running reads, and it does not cover the WSL2 file-sharing cache bug that appeared when containers were paused and resumed around backups. It shows the locks work today, not that the mount is beyond suspicion — which is what the Database health check is for.
- Because the Audit view opens with live counts, its DB-check queries must stay cheap and bounded; a check that gets slow moves to click-only.
- The tab is deliberately not a pure database view: disk checks `stat` files and scan `imported/`. That is read-only and click-only, and it is what catches a "completed" track whose file has vanished.
- New dashboard code and `TrackDB` read methods ship to the gated environment only through `invoke deploy`. Tests follow the existing pattern: temp-DB tests for the `TrackDB` methods and a `tests/test_dashboard_database.py` for the routes.
